# 代码审查报告（静态阅读，未实机验证）

## 高优先级问题

### 1. Flash HAL 返回值未检查

`Boot_WriteFlag()`、`Boot_ErasePage()` 和 `Boot_ProgramBuf()` 对擦除/编程调用的返回值及 `page_err` 未作错误处理。Flash 写入失败时，后续流程仍可能继续并给出 ACK。建议逐次检查返回值，失败时停止当前升级、保留可恢复状态并记录错误。

### 3. APP 跳转前未验证向量表

`Boot_JumpToApp()` 直接读取 APP 的初始 MSP 和 Reset Handler 并跳转，没有检查 MSP 是否落在合法 RAM 范围、Reset Handler 是否位于 APP Flash 范围。升级损坏或空白时可能跳转异常。建议校验向量值，并在验证失败时停留 Bootloader。

### 4. 升级标志的擦写失败未处理

标志页每次更新均擦除整页，再写半字，但没有检查擦除和编程是否成功。需确认 APP 触发升级与 Bootloader 状态迁移在掉电边界下的行为。

## 中优先级问题

### 3. 擦除粒度与接收块大小需要按实际芯片确认

`CHUNK_SIZE` 为 `0x400`（1024 字节），每个接收块调用一次 `Boot_ErasePage(APP_ADDR + off)`。若目标芯片确实采用 1 KiB Flash 页且 `APP_ADDR` 按页对齐，这一粒度在地址设计上匹配；但仍需对照实际 MCU 完整料号、数据手册与 HAL 实现确认。当前报告没有通过编译或实机擦写验证这一点。

### 4. CRC32 不等于固件认证

CRC32 适合检测传输错误，不抵御恶意修改。当前源码静态检查未发现固件数字签名验证。若考虑安全 OTA，应加入签名验证和密钥管理。

### 5. 当前方案没有 A/B 回滚

源码直接覆盖 APP 区，标志 `FLAG_INPROGRESS` 可让 Bootloader 保持升级等待，但不等于具备旧版本备份或自动回滚能力。需要通过断电实验确认恢复操作，并在文档中明确限制。

### 6. 最后一字节的半字编程填充

`Boot_ProgramBuf()` 在 `len` 为奇数时将最后一个半字的高字节填为 `0x00`。建议按芯片编程约束评估是否应填充 `0xFF`，并用奇数长度 BIN 做测试。

### 7. UART 接收与 ACK 协议边界需测试

接收逻辑使用固定超时和文本 ACK。需检查发送端对半包、粘包、丢 ACK、重发及超时的处理，特别是 Wi-Fi 透传时数据流是否严格按长度同步。
